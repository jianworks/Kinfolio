# 現金規劃功能研究

研究日期：2026-10-27。範圍是需求與整合設計，尚未實作或部署。來源為 `../../Budget.xlsx` 的 `Cash Flow (Month)` 工作表，以及本機 Kinfolio 程式碼。試算表未標年度與資料更新日，不可直接視為 2026 年實際帳況。本文不複製完整個人收支明細。

## 已確認範圍

依使用者補充：所有金額固定為台幣，介面不提供幣別選擇；功能獨立估算月度現金流，不與既有資產、投資帳戶或貸款資料關聯。銀行帳戶連結、精確入扣款日期與外幣支付能力不列入本提案的開發階段。

原表的保留算法有三項限制：只看期間終點，不能保證中途不短缺；可能算出負的應保留金額（C32 即如此）；年底無完整下一年度資料。負值不應直接當成可以多提領的現金。產品應提供原表規則供核對，正式指標採下述逐月需求。

## 建議產品體驗

新增主選單「現金規劃」。使用者先選持有人、規劃月份、期初現金及安全底線，再輸入收入和支出。採台幣月度模型，手動輸入期初可用現金，與既有資產資料獨立；介面只標示金額單位，不提供幣別選擇。

頁首先回答三件事：目前需要保留多少、可以調度或需要補多少、預測何時低於安全底線。下方是現金餘額與安全底線的曲線，以及可編輯月表。點進缺口月份可看到該月與之前月份的收入、支出及主要項目。

月表列出收入、支出、淨流量、預測月底現金、應保留金額與差額；支出項目可展開。桌面版可貼上連續月份數字，手機版按月份編輯。保留「薪資四月起調整」及「某月額外費用」等簡單覆寫，第一版不必建立複雜週期引擎。

預設規劃未來 12 個月，但必須先補足跨年資料；沒有下一年度資料時顯示範圍與缺資料提示，不假設空白為零。新年度可複製固定項目，獎金、稅及旅遊等金額仍需確認。欄位要區分「已確認無此收支（0）」與「尚未填寫」。

## 計算規則

以下是產品提案，並非宣稱原表使用此算法。收入、支出輸入正金額，以方向區分；計算時支出扣除。

設 B 為基準月底已確認現金，n_i 為之後第 i 月的收入減支出，F_j 為第 j 月安全底線：

```
預測月底現金 P_j = B + Σ(i=1..j) n_i
應保留現金 R = max(0, F_0, max(j=1..H)[F_j - Σ(i=1..j) n_i])
呈現的保留額 = ceil(R / roundUnit) × roundUnit
可調度額 = max(0, B - 呈現的保留額)
待補足額 = max(0, 呈現的保留額 - B)
```

F_0 是基準日自身的底線。roundUnit 預設可選萬元以接近原表，但安全底線由使用者設定；「下一月薪資」只是原表推導出的候選預設，不能擅自當作已確認的緊急預備金政策。圖表用未取整預測值，展示保留額時單獨說明取整。

月末規劃無法確認月內扣款先於薪資入帳時是否短缺，頁面需直接標示「以月底餘額估算」。本功能維持月度估算，不安排逐日計算或精確入扣款日期。

驗收反例（虛構數字）：期初 10 萬、底線 3 萬，未來三月淨流量 -8 萬、+10 萬、-1 萬。所需保留額為 11 萬，待補 1 萬，第一月餘額 2 萬。只看期末會漏掉第一月低於底線的問題。

若基準日在月中，須讓使用者填「本月剩餘收支」或改以已核對月底作為基準，不能把已發生的整月支出再扣一次。新增實際月底餘額後，預測從新基準往後跑；過去計畫仍保留，實際差異顯示為對帳差額，不自動解釋為投資移轉。

## 與 Kinfolio 的邊界

現有資產與目標是投資價值、投入本金和貸款餘額模型，不能直接拿來當生活帳戶現金流。來源見 [README](../README.md)、[初始資料結構](../migrations/0001_initial.sql)、[持股資料結構](../migrations/0003_portfolios.sql)。

- 現金餘額、收入與支出皆由使用者手動填寫，只用於本計畫的估算。
- 不讀取、連結或更新既有資產、券商現金、投資本金、貸款餘額與交易事件，也不將規劃餘額加入總資產。
- 房貸等項目可自行填入預估月付金額，不從既有貸款資料推算。
- 沿用登入者隔離。第一版每個計畫綁定單一持有人；跨持有人共同生活池需另行明確設計，不改動「全部持有人不合計資產」的既有規則。

## 建議實作切分

1. 新增純計算模組 `public/cash-plan-domain.js`：月份鍵、金額驗證、單月覆寫、預測、最大累計缺口與取整。前後端共用，金額延用最小單位整數與安全範圍驗證。
2. 新增遷移（檔名依實作時最新序號決定）：`cash_plans` 保存持有人、期間、安全底線、取整（全部金額固定為台幣，不設可選幣別）；`cash_plan_items` 保存名稱、分類與方向；`cash_plan_months` 保存每項每月金額與確認狀態；`cash_balance_snapshots` 保存現金基準日與金額。先存明確月額，避免規則與覆寫衝突。
3. 新增計畫 API 與前端頁面，沿用現有驗證、來源檢查、版本控制與重送防護；所有資料引用以 user_id 驗證。計畫輸入存檔，衍生結果由共用模組重算。
4. 更新備份版本與完整內容（目前備份尚無匯入），加入新資料。不可把「提供備份」描述成已支援還原。
5. 新增計算單元測試及 Worker/D1 整合測試。UI 驗證缺資料、年月跨界、實際/預測標籤與手機編輯。正式部署另外處理。

重要測試：中途缺口但年底正值、全部正流量、負的原表保留額、無未來月份、跨年缺資料、0 與空白、月中基準、月份覆寫、四捨五入/萬元進位邊界、錯誤持有人與跨登入者引用、重送與並行修改、備份包含完整新資料。

## 導入 Budget.xlsx

第一版可用月表貼上，避免做通用 Excel 公式執行器。若提供此檔專用匯入，流程應先選年度、持有人、實際餘額截止月份及安全底線，再預覽分類與月份金額。僅將 C2:N27 的月金額轉為計畫；第 29、30、32、34 列重新計算。C33:N33 要由使用者確認哪些是實際值，未確認的預測不匯入為實際。

匯入要檢查公式有無可用結果；缺結果不得當 0。原表沒有足夠資訊自動分解所有週費用及混合一次性項目，因此先保存月額與來源位置，匯入完成後才讓使用者整理分類。匯入預覽不立即修改投資帳本。

## 推進順序

第一階段完成手填台幣現金基準、12 個月收支表、固定金額底線、逐月缺口與明確期間。第二階段加入 Excel 匯入與保守收入情境（例如不計獎金）。銀行帳戶連結、精確入扣款日期、外幣支付能力及既有資產關聯均不在本次規劃範圍。

實作前最需要確認的業務定義是：原表「下一月薪資」是否確實代表想保留的安全底線，以及應預留至年底還是持續滾動 12 個月。可先依固定底線、滾動 12 個月設計，保留設定調整能力。
